# 密钥与加密运维手册（P1-24）

对应计划：03 章 3.1、11 章 11.2 第 2 条、12 章 12.9 第 10 条。

## 一、密钥是怎么分层的

| 层 | 是什么 | 放在哪里 | 谁能读到 |
|---|---|---|---|
| 主密钥 | 32 字节（64 位十六进制）。只用来包裹数据密钥 | 环境变量（`ENCRYPTION_MASTER_KEYS` 或沿用的 `TOKEN_ENCRYPTION_KEY`）；部署专项后可改为云密钥管理（主密钥留在云端） | 接口服务与后台任务进程 |
| 数据密钥 | 按用途一把、带版本：`amazon-token`（亚马逊刷新令牌）、`buyer-pii`（买家个人信息）、`mfa`（多因素认证密钥） | 数据库表 `DataEncryptionKey`，**只有被主密钥包裹后的密文**；租户连接账号无权限，系统账号只增不删 | 两个进程（用主密钥解开） |
| 机密 | 令牌、买家信息、多因素密钥 | 各业务表里的密文列，格式 `nk2.<数据密钥版本>.<iv>.<标签>.<密文>` | 见下 |

**谁能解密什么**（接口服务被攻破时的影响面）：

- 亚马逊刷新令牌：接口服务**只能加密、没有解密入口**；解密只发生在后台任务里（拿它向亚马逊换访问令牌）。
- 买家个人信息：只有后台任务写入；接口服务既不加密也不解密。
- 多因素认证密钥：接口服务可加密、可解密（校验验证码需要）。

密文还绑定用途与版本（认证附加数据），把令牌密文拿去按买家信息解密一定失败。

## 二、日常：什么都不用做

首次启动时两个进程会自动创建三类数据密钥的第一版（并发创建以先成功的为准）。启动检查会确认主密钥能解开已有数据密钥，配置不对**直接拒绝启动**。

查看状态（不显示任何密钥内容）：

```
corepack pnpm --filter @nova/worker build
corepack pnpm --filter @nova/worker keys status
```

## 三、轮换数据密钥（建议每年一次，或怀疑泄露时立即做）

1. `keys rotate all`（或 `keys rotate amazon-token` 只轮换某个用途）：生成新版本，旧版本退役但仍可解密。新写入最迟在 60 秒内全部改用新版本（各进程有缓存）；读取任何版本都立即可用。
2. `keys reencrypt`：把仍在用旧版本或改造前旧格式的密文迁到当前版本。可随时中断、重复运行；读取后若密文被别处改动则不覆盖，计为失败，下次再处理；解不开的行只输出行编号（退出码 2），需人工核查。
3. 再运行一次 `keys reencrypt`，全部为 0 迁移、0 失败，即完成。

## 四、轮换主密钥（人员离职、怀疑环境变量泄露时）

1. 生成新主密钥：`node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"`。
2. 同时配置新旧两把，并指定新包裹用哪一把，**先在所有进程上线**：
   ```
   ENCRYPTION_MASTER_KEYS=new-2026:<新的>,old:<旧的>
   ENCRYPTION_MASTER_KEY_ACTIVE=new-2026
   ```
   沿用 `TOKEN_ENCRYPTION_KEY` 的部署，它自动作为编号 `env-1` 的主密钥保留，不要删除，直到第 4 步。
3. `keys rewrap`：用新主密钥重新包裹所有数据密钥。**不动任何业务密文**，几秒即完成。
4. 确认所有进程都已用新配置运行后，从环境变量中移除旧主密钥。

> 旧主密钥移除后，若仍有数据密钥由它包裹，启动检查会报错并拒绝启动；所以务必先 `rewrap` 再移除。

## 五、关于改造前的旧密文

升级前保存的令牌、买家信息、多因素密钥是旧格式（三段式，直接用 `TOKEN_ENCRYPTION_KEY` 加密）。升级后仍可读取；`keys reencrypt` 会把它们迁到新格式。**迁完之前不要更换或删除 `TOKEN_ENCRYPTION_KEY`**（它同时是旧密文的根密钥）。

### 退货买家备注（P6-14）

退货的买家备注与订单买家信息用同一用途（`buyer-pii`）加密，`keys reencrypt` 会一并处理 `FbaReturnCase.customerCommentsCipher`。升级前的明文备注（`customerComments` 列）由 worker 每小时的清理任务逐批加密并清空明文；要立即处理，运行 `keys backfill-return-comments`（可重复运行；输出只有数量与出错行编号，不输出内容）。确认没有明文后，才可运行 `database/ops/drop-return-comment-plaintext.sql` 删除明文列（脚本带检查，还有未加密的行会拒绝；删除后要还原只能重新加回空列，已清空的明文无法找回）。

## 六、备份与灾难恢复

- 数据密钥表与业务表一起备份；主密钥**单独**保管（与数据库备份不放在同一处）。
- 丢失主密钥 ＝ 丢失全部机密：令牌需要卖家重新授权，多因素需要重新绑定，买家信息需要重新同步。
- 数据库回滚脚本会丢弃数据密钥表，执行前先确认没有新格式（`nk2.` 开头）密文，见迁移目录的 `rollback.sql`。

## 七、云密钥管理（随部署专项接入）

已预留接入点：实现 `@nova/crypto` 的 `KmsClient`（`encrypt`/`decrypt`，把数据密钥交给云端包裹），设置 `ENCRYPTION_KEY_PROVIDER=kms` 与 `KMS_KEY_ID`。切换步骤与主密钥轮换相同：`rewrap` 会用云端密钥重新包裹所有数据密钥，业务密文不动。
