# 索引评审流程（P1-27）

依据：`freeze/models.md` 0.2 索引规范第 4 条；12 章 12.4 后端；14 章 P1-27。

## 1. 什么时候必须评审

满足任一条件的改动，必须按本流程评审后才能合并：

- 新增或修改列表、汇总、导出、图表所用的查询（含筛选、排序、游标分页条件变化）；
- 新增或修改工作进程中的批量读取、刷新任务；
- 新增表，或给已有表新增会被查询使用的列。

## 2. 评审要求

| 序号 | 要求 | 如何证明 |
| --- | --- | --- |
| 1 | 查询条件的第一列为租户，其后是店铺、日期（与 0.2 第 1 条一致） | 查询语句与索引定义对照 |
| 2 | 查询能走索引，关闭顺序扫描后执行计划里不再出现顺序扫描 | 测试中调用 `expectIndexedQuery`（`apps/api/src/testing/explain.ts`），测试文件命名 `*.db.test.ts` |
| 3 | 排序字段与游标字段为非空列，且排序键之后补充主键保证翻页不重不漏 | 游标分页用 `CursorService`（复合游标 = 排序字段值 + 编号）；评审人核对排序字段是否非空 |
| 4 | 外键列单独有索引 | `index-rules.db.test.ts` 规则 2，已知例外清单为空，**不得新增例外** |
| 5 | 分区表的查询带上分区列范围（下单时间、发生时间等），否则会扫描全部分区 | 评审人核对查询；执行计划里的分区数量应与时间范围匹配 |
| 6 | 带租户列的表至少有一个以租户列开头的索引；分区表的主键与全部唯一索引包含分区列 | `index-rules.db.test.ts` 规则 1、3、4 |
| 7 | 唯一键即幂等键，同时作为 upsert 的冲突目标 | 对应工作包的幂等测试 |

## 3. 新增索引的写法

1. 在 `schema.prisma` 的模型里添加 `@@index`，列顺序按 2 中第 1 条；
2. 手写迁移 SQL（`CREATE INDEX IF NOT EXISTS`），同目录放 `rollback.sql` 写明回滚（`DROP INDEX IF EXISTS`）；
3. 大表（预计超过百万行）新增索引使用 `CREATE INDEX CONCURRENTLY`，该语句不能放在事务里，迁移需单独拆成一个文件并在迁移说明里写明；分区表不支持对父表使用 `CONCURRENTLY`，需先对各分区逐个创建，再创建父表索引并挂接；
4. 运行 `corepack pnpm exec vitest run --project api-db`，其中 `schema.db.test.ts` 保证迁移与 `schema.prisma` 零差异。

## 4. 上线后的监控

- 数据库与应用两层都记录慢查询：超过 1 秒（`SLOW_QUERY_MS` 可调）输出 `slow_query` 告警，内容为压缩后的语句文本与耗时，不含参数；
- 工作进程每日检查默认分区；默认分区出现数据输出 `default_partition_has_rows` 告警，说明有记录的日期超出已建分区；
- 慢查询告警出现后，评审人用 `EXPLAIN (ANALYZE, BUFFERS)` 在与生产同规模的数据上复核，结论与处理记录在变更单中。

## 5. 运行要求

分区表数量较多时，单个事务可能锁定大量分区。数据库必须设置 `max_locks_per_transaction` 不小于 512（`infrastructure/compose/docker-compose.yml` 已配置，部署时同样需要）。
